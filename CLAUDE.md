# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

An **IBM Content Navigator (ICN) plug-in** ("DynamicQueries", version reported by `DynamicQueries.getVersion()`). It is packaged as a single JAR that an ICN administrator registers in the ICN admin tool; ICN loads the Java classes server-side and serves everything under `WebContent/` to the browser. The project was generated from the ICN plug-in Eclipse template. The feature being built is **DQ**: it hosts ICN's native search builder, serializes the query the user defines (document class, fields, conditions, groups) and saves it, together with the equivalent CE SQL, in the DQ microservice (separate repo `icn-api-dynamic-queries`, `/api/v1/query` and `/api/v1/project`), which the browser calls directly; all queries target the single repository configured for the plug-in. Each query stores its CE SQL and, in `config`, the definition that reopens it in the builder (the `QueryDefinition` schema of `docs/api/dynamic-queries.openapi.yaml`, an earlier draft whose endpoints are no longer used). The feature config pane and the global script are still empty stubs.

## Build

Ant is the only build system (no Maven/Gradle, no linter):

```sh
ant            # default target "all" = clean, compile, jar → ./DynamicQueriesICNPlugin.jar
```

- Compiles with `source/target 1.8` — don't use Java 9+ language features or APIs.
- Dependencies live in `lib/`: `navigatorAPI.jar` (ICN API, `com.ibm.ecm.extension.*`), `j2ee.jar` (servlet API) and `Jace.jar` (P8 CE API, compile-only: ICN provides it at runtime, never bundle it). `lib/` is git-ignored because this is a public repo and the jars are proprietary — each developer supplies them locally. Never commit them. `build.xml` and `.classpath` reference them by relative path; `.classpath` uses the generic `JRE_CONTAINER`, so keep it free of machine-specific absolute paths.
- The `jar` target copies `src/**/WebContent/**` into the JAR alongside the classes and writes the manifest `Plugin-Class: co.com.portalup.extension.DynamicQueries`. `META-INF/MANIFEST.MF` in the repo is a reference copy; the build generates its own.
- `bin/` is Eclipse's output folder, not used by Ant.
- Tests: `node test/QuerySerializer.test.js` (plain Node, no dependencies; a minimal `define` shim loads the AMD module).

Deploying/testing means loading the built JAR into a running ICN instance (admin tool → Plugins), then enabling the feature on a desktop.

## Architecture

Java side (`src/co/com/portalup/extension/`):
- `DynamicQueries.java` — the `Plugin` subclass (entry point named in the manifest). Declares the plug-in id, the global script `DynamicQueries.js`, CSS `DynamicQueries.css`, the Dojo module path `dynamicQueriesDojo`, the plug-in config dijit, and returns the feature list. New actions, services (`PluginService`), filters, menus, etc. must be instantiated and returned from the corresponding `get*()` array here, or ICN won't see them.
- `SettingsService.java` — the only `PluginService` (id `SettingsService`): returns the plug-in settings the browser needs, `{ ok, data: { repositoryId, projectsApiUrl, canDesign } }` (always HTTP 200; `{ ok: false, error }` on failure). `projectsApiUrl` comes from `PluginConfiguration.getProjectsApiUrl`: while the config was never saved it is `DEFAULT_PROJECTS_API_URL` = `https://localhost:8443/api/v1`, mirrored in `ConfigurationPane.js`. `canDesign` is true when `designerGroups` is empty, otherwise only if the user belongs (case-insensitive, short name / name / DN) to one of those P8 groups in the configured repository, read by `P8UserGroups` (`User.MemberOfGroups` with the user's `getP8Subject`); if that read fails the service answers `USER_GROUPS_UNAVAILABLE`. Logic lives in `handle(configuration, userGroups)`, which doesn't take `PluginServiceCallbacks` (can't be instantiated outside ICN) so it can be tested. If a service ever needs an operation param, don't call it `action` (ICN overwrites it with the service id).
- `PluginConfiguration.java` — parses the plug-in configuration (`repositoryId`, `projectsApiUrl`, `designerGroups`: P8 groups separated by `;` or newlines, since DNs contain commas) saved by `ConfigurationPane.js`; the names must match. `repositoryId` is the single repository queries are designed and saved against. `projectsApiUrl` (name kept for saved configs) is the base URL of the DQ microservice (queries and projects) (separate repo `icn-api-dynamic-queries`), which the **browser** calls directly — it must be reachable from the user's machine and allow CORS from the ICN origin (`cors.allowed-origins` in that service), and it must be **https**: ICN's Content-Security-Policy (`default-src 'self' blob: https:`) blocks `http:` URLs other than ICN itself (the service's `local` profile serves HTTPS on 8443 with a self-signed cert).
- `DQ.java` — a `PluginFeature` (left-side launch bar feature, id `DQ`). Its `getContentClass()` → `dynamicQueriesDojo.DQ` and `getConfigurationDijitClass()` → `dynamicQueriesDojo.FeatureConfigurationPane` link it to the client widgets.

Client side (`src/co/com/portalup/extension/WebContent/`, Dojo AMD):
- `DynamicQueries.js` — global script loaded before login.
- `dynamicQueriesDojo/` — registered by ICN as the `dynamicQueriesDojo` module path; each widget has an HTML template in `templates/` loaded via `dojo/text!`.
  - `DQ.js` — the feature pane, extends `ecm/widget/layout/_LaunchBarPane` (implement `loadContent`/`reset`; `isLoaded`/`needReset` control lifecycle). Leading pane: the repository configured for the plug-in (`repositoryId`, read-only; fetched with `SettingsClient.getSettings`, "Nueva consulta" and "Proyectos" stay disabled until it resolves in the desktop), "Nueva consulta" and a `dijit/Tree` whose "Consultas guardadas" folder holds one subfolder per project with its queries, from `DqApiClient.listProjectQueryCompose` (`refreshTree`; projects and queries sorted by name, inactive ones marked; query items are keyed by `projectQueryId` because a query can belong to several projects; queries without a project don't appear). The tree is refreshed after saving a query and after closing "Proyectos". Clicking a query opens it; the context menu offers Abrir / Ejecutar / Eliminar (Eliminar first deletes the query's project associations: the service refuses with 409 to delete an associated query). `openSavedQuery` parses the query's `config` (the stored definition) and rebuilds the ICN `SearchTemplate` (`QuerySerializer.toSearchTemplate`); queries whose `config` isn't a definition (created outside the plug-in) can't be opened and reuses the tab if the query is already open. Center: a `StackContainer` switching between an empty state and a `TabContainer` of `QueryTab`s. Access: if `canDesign` is false the pane shows only a no-access notice (`dqAccessDenied` class) — this only hides the UI; the microservice is called from the browser and doesn't know the ICN user. ICN reuses the pane across logout/login in the same tab, so `onLogout` clears it (tabs, tree, permission) and `onLogin` reloads it if selected.
  - `QueryTab.js` — one tab per query: a subclass of ICN's `ecm/widget/search/SearchBuilder` (criteria, Buscar, results) with the parts DQ doesn't use hidden via the `dqHiddenAction` class: P8 save buttons, "Buscar en"/"Opciones de búsqueda" (always root folder, documents, released version), "Visualización de resultados", "Mostrar todas las propiedades", "Buscar en varias clases" and "Incluir todas las propiedades" in the class dropdown (hidden, unchecked and disabled, so multi-class mode can't be triggered), and in the results toolbar "Añadir documento", "Exportar todo" and "Acciones" (`getContentListModules` configures the `Toolbar2` module). `DQ` acts as its `tabContainer`/`parentPane` (`closeTab`, `openTab`, `openSearch`). The ICN search API as verified on 3.0.10 is documented in `docs/icn-search-api.md`. "Ver JSON" shows the query definition.
  - `QuerySerializer.js` — both directions between the ICN builder and the API contract's `QueryDefinition`. `serialize(searchDefinition, repository)` reads the form without running the search; `build(state)` (pure) converts it and validates. `toIcnSearch` (pure) / `toSearchTemplate` go back: contract → the JSON ICN uses for saved searches → `SearchTemplate` the builder can open. `toCeSql(definition)` (pure) produces the P8 CE SQL: `Id` + result columns (`{NAME}` → `DocumentTitle`), class `WITH INCLUDESUBCLASSES|EXCLUDESUBCLASSES`, conditions/groups, `INFOLDER`/`INSUBFOLDER`, version (`VersionStatus = 1` / `IsCurrentVersion = TRUE`), `ORDER BY`; datetimes as UTC literals (`20260101T050000Z`); `IN` is expanded to `=` … `OR` (single-valued properties). Pure parts are unit-tested.
  - `SaveQueryDialog.js` — "Guardar consulta" (ICN `BaseDialog`): saves `{ name, cesql, config, status }` with `DqApiClient.createQuery`/`updateQuery` (update when the query has an `id`) and then, with the query id, its project association (`/project-query`, `{ projectId, queryId, config }` where `config` is the "Ruta de configuración" field). The user enters name (max 100), project (required select of active projects), configuration path (required, max 1024) and status; when editing, the current association preselects project and path and is updated only if they changed. If the association fails for a new query, the query is deleted again (if that also fails, the dialog keeps its id so a retry updates it). `cesql` (max 512) comes from `QuerySerializer.toCeSql` and is shown read-only; `config` (max 1024) is the definition as JSON. Over a limit, or with definition errors, Guardar stays disabled with the reason. `QueryTab` keeps the saved query in `savedQuery` and fires `onQuerySaved`.
  - `ProjectsDialog.js` — "Proyectos" (ICN `BaseDialog`, button in the leading pane below "Nueva consulta"): full CRUD of projects. A toolbar (Nuevo / Editar / Eliminar / Actualizar + status filter), a plain HTML table as the grid (click selects, double-click edits) and an inline fieldset form between the toolbar and the table (name and description required, max 100 each; status ACTIVE/INACTIVE). Errors and confirmations go to the dialog's `setMessage`; delete asks with `ConfirmationDialog`.
  - `DqApiClient.js` — `dojo/request/xhr` client for the DQ microservice, called from the browser (not through ICN); `baseUrl` (`projectsApiUrl`) is set by `DQ` from `SettingsClient.getSettings`. Projects: `listProjects(status?)`, `getProject`, `createProject`, `updateProject`, `deleteProject` over `{baseUrl}/project[/{id}]` (`{ id, name, description, status, createdAt }`). Queries: `listQueries(status?)`, `getQuery`, `createQuery`, `updateQuery`, `deleteQuery` over `{baseUrl}/query[/{id}]` (`{ id, name, cesql, config, status }`). `listProjectQueryCompose()` → `GET {baseUrl}/project-query-compose` (projects with their `queries`, each with `projectQueryId`/`projectQueryConfig`/`projectQueryStatus`). Project–query associations: `listProjectQueries({ projectId, queryId, status })`, `createProjectQuery`, `updateProjectQuery`, `deleteProjectQuery` over `{baseUrl}/project-query[/{id}]` (`{ id, projectId, queryId, config, status, createdAt }`; 409 if the pair exists); treats HTTP status 0 as a failure (dojo/request counts it as success); rejects with `{ status, code, message }` (maps the service's `ErrorResponse`, including `details`).
  - `SettingsClient.js` — promise wrapper over `ecm/model/Request` for `SettingsService` (`getSettings`); rejects with `{ code, message }`.
  - `ConfigurationPane.js` — plug-in–level admin config (extends `ecm/widget/admin/PluginConfigurationPane`): repository of the queries (required; a select filled with ICN's P8 repositories via `ecm.model.admin.appCfg.getRepositoryObjects`), the DQ microservice base URL, and the groups allowed to use the designer (`designerGroups`, empty = everyone).
  - `FeatureConfigurationPane.js` — per-desktop feature config; `load()` reads `this.configurationString`, `save()` must serialize values back into it.

String identifiers are the glue between the Java and JS halves: the Dojo module name, widget class names, file names and the plugin/feature ids returned in Java must match the JS `define`/`declare` names and file paths exactly. Plug-in and feature ids must be alphanumeric (used in URLs). Keep `declare` names in the lowercase `dynamicQueriesDojo.*` namespace.

CSS in `DynamicQueries.css` is loaded globally into ICN, so scope every feature rule under `.dqPane`; dialogs are attached to `<body>`, so scope theirs under their own `dq*Dialog` class.

# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## What this is

An **IBM Content Navigator (ICN) plug-in** ("DynamicQueries", version reported by `DynamicQueries.getVersion()`). It is packaged as a single JAR that an ICN administrator registers in the ICN admin tool; ICN loads the Java classes server-side and serves everything under `WebContent/` to the browser. The project was generated from the ICN plug-in Eclipse template. The feature being built is **DQ**: it hosts ICN's native search builder, serializes the query the user defines (document class, fields, conditions, groups) and saves it, together with the equivalent CE SQL, in the DQ microservice (separate repo `icn-api-dynamic-queries`, `/api/v1/query` and `/api/v1/project`), which the browser calls directly; all queries target the single repository configured for the plug-in. Each query stores its CE SQL and, in `config`, the definition that reopens it in the builder (the `QueryDefinition` schema of `docs/api/dynamic-queries.openapi.yaml`, an earlier draft whose endpoints are no longer used). The feature config pane is still an empty stub.

## Build

Ant is the only build system (no Maven/Gradle, no linter):

```sh
ant            # default target "all" = clean, compile, jar → ./DynamicQueriesICNPlugin.jar
```

- Compiles with `source/target 1.8` — don't use Java 9+ language features or APIs.
- Dependencies live in `lib/`: `navigatorAPI.jar` (ICN API, `com.ibm.ecm.extension.*`), `j2ee.jar` (servlet API) and `Jace.jar` (P8 CE API, compile-only: ICN provides it at runtime, never bundle it). `lib/` is git-ignored because this is a public repo and the jars are proprietary — each developer supplies them locally. Never commit them. `build.xml` and `.classpath` reference them by relative path; `.classpath` uses the generic `JRE_CONTAINER`, so keep it free of machine-specific absolute paths.
- The `jar` target copies `src/**/WebContent/**` into the JAR alongside the classes and writes the manifest `Plugin-Class: co.com.portalup.extension.DynamicQueries`. `META-INF/MANIFEST.MF` in the repo is a reference copy; the build generates its own.
- `bin/` is Eclipse's output folder, not used by Ant.
- Tests: `node test/QuerySerializer.test.js` (plain Node, no dependencies; a minimal `define` shim loads the AMD module).

Deploying/testing means loading the built JAR into a running ICN instance (admin tool → Plugins), then enabling the feature on a desktop. ICN serves plug-in files (`/navigator/plugin/DynamicQueries/getResource/…`) with `Last-Modified` but no `Cache-Control`, so after a redeploy browsers may keep running the old JS/CSS for a while; a hard reload doesn't help because ICN loads them dynamically. Test in a fresh/incognito window or clear the cache (a resource with `transferSize` 0 in `performance.getEntriesByType("resource")` came from cache).

## Architecture

Java side (`src/co/com/portalup/extension/`):
- `DynamicQueries.java` — the `Plugin` subclass (entry point named in the manifest). Declares the plug-in id, the global script `DynamicQueries.js`, CSS `DynamicQueries.css`, the Dojo module path `dynamicQueriesDojo`, the plug-in config dijit, and returns the feature list. New actions, services (`PluginService`), filters, menus, etc. must be instantiated and returned from the corresponding `get*()` array here, or ICN won't see them.
- `SettingsService.java` — `PluginService` (id `SettingsService`): returns the plug-in settings the browser needs, `{ ok, data: { repositoryId, projectsApiUrl, canDesign } }` (always HTTP 200; `{ ok: false, error }` on failure). `projectsApiUrl` comes from `PluginConfiguration.getProjectsApiUrl`: while the config was never saved it is `DEFAULT_PROJECTS_API_URL` = `https://localhost:8443/api/v1`, mirrored in `ConfigurationPane.js`. `canDesign` is true when `designerGroups` is empty, otherwise only if the user belongs (case-insensitive, short name / name / DN) to one of those P8 groups in the configured repository, read by `P8UserGroups` (`User.MemberOfGroups` with the user's `getP8Subject`); if that read fails the service answers `USER_GROUPS_UNAVAILABLE`. Logic lives in `handle(configuration, userGroups)`, which doesn't take `PluginServiceCallbacks` (can't be instantiated outside ICN) so it can be tested. If a service ever needs an operation param, don't call it `action` (ICN overwrites it with the service id).
- `ExecuteQueriesService.java` — `PluginService` (id `ExecuteQueriesService`) for "Resultados de consultas": POST body `{ queries: [ { name, cesql, config } ] }` (sent by `ExecuteQueriesClient` with `Request.postPluginService`; the body is read from the `json_post` attribute/parameter if ICN already consumed it, otherwise from the request), `cesql` with the wildcards already filled and `config` the association's grouping path. Runs each one (only `SELECT`, max 50 queries, 1000 documents each) in the configured repository with the user's P8 session (`getP8Subject`/`getP8ObjectStore`), fetching the label properties with a `PropertyFilter` instead of adding them to the SELECT (classes without them would fail). Answers `{ ok, data: { tree, failures: [ { name, message } ], truncated } }`; a failing query doesn't stop the rest. Never name a response field `errors`: ICN shows its own dialog for it. Logic in `handle(body, repositoryId, executor)`, testable without ICN.
- `DocumentPropertiesService.java` — `PluginService` (id `DocumentPropertiesService`) for the document chosen in "Resultados de consultas", port of `/portalUpApp/api/documents/properties` (`DocumentQueryController` + `S3Service` of the consulta general): POST `{ documentId }` (GUID), read in the configured repository with the user's P8 session; properties in class order, without the consulta general's `SYSTEM_PROPERTIES` nor object/binary ones, formatted like its `FilenetDataTypeFormatter` (choice-list display name, dates `dd/MM/yyyy`, lists joined by commas). If the document has `file_key` and `storage_name` it is in S3: the **ICN server** GETs `{s3DownloadUrl}?storage_name=…&file_key=…` with header `x-api-key: {s3ApiKey}` and returns the body (base64; JSON quotes stripped). Answers `{ ok, data: { properties: [ { name, label, value } ], s3, mimeType (DocumentTree.mimeType), file, fileError } }`; a failed download still returns the properties with `fileError`. Logic in `handle(body, reader, downloader)`, testable without ICN. Shares `readBody`/`write`/`failure` with `ExecuteQueriesService`.
- `DocumentTree.java` — pure (no P8/ICN types) port of `DocumentTreeBuilder` from the consulta general backend (Prote_ConsGral): parses the grouping config (`{ vnRoot: "A,B,C" }` or `{ vnRoot: [ { name: "A" }, … ] }`, not JSON, read with regexes like `parseConfigMap`), merges same-named folders per level, skips documents without a path and builds the same JSON as `/portalUpApp/api/documents/queryContent` (`{ text, type: "Virtual", index, data, children }` / document nodes with `text`, `mimeType`, `iconCls`, `data: { objectStoreName, objId }`, `viewerUrl`…). Label `TipoDocumento [RadicadoProteccion without extension | DocumentTitle]` (the consulta general shows the TAP8_PRO_TIPOS_DOC description, an Oracle table the plug-in can't read, so here it's the raw value; without `TipoDocumento` only the name); MIME type inferred for S3 documents as there.
- `PluginConfiguration.java` — parses the plug-in configuration (`repositoryId`, `projectsApiUrl`, `designerGroups`: P8 groups separated by `;` or newlines, since DNs contain commas; `s3DownloadUrl`/`s3ApiKey`: the S3 download service used by `DocumentPropertiesService`, called server-side, the key never goes to the user's browser — don't add it to `SettingsService`) saved by `ConfigurationPane.js`; the names must match. `repositoryId` is the single repository queries are designed and saved against. `projectsApiUrl` (name kept for saved configs) is the base URL of the DQ microservice (queries and projects) (separate repo `icn-api-dynamic-queries`), which the **browser** calls directly — it must be reachable from the user's machine and allow CORS from the ICN origin (`cors.allowed-origins` in that service), and it must be **https**: ICN's Content-Security-Policy (`default-src 'self' blob: https:`) blocks `http:` URLs other than ICN itself (the service's `local` profile serves HTTPS on 8443 with a self-signed cert).
- `DQ.java` — a `PluginFeature` (left-side launch bar feature, id `DQ`). Its `getContentClass()` → `dynamicQueriesDojo.DQ` and `getConfigurationDijitClass()` → `dynamicQueriesDojo.FeatureConfigurationPane` link it to the client widgets.
- `DQResults.java` — second `PluginFeature` (id `DQResults`, "Resultados de consultas", content class `dynamicQueriesDojo.DQResults`, icon class `DQResultsLaunchIcon`). Not restricted by `designerGroups`.

Client side (`src/co/com/portalup/extension/WebContent/`, Dojo AMD):
- `DynamicQueries.js` — global script loaded before login. Hides the `DQ` launch-bar button (toolbar style) / menu entry (flyout style) unless `SettingsService.canDesign` is true; hidden while unknown. It polls `Desktop.connected`/`userId` every 500 ms instead of using ICN events: on 3.0.10 the layout is built before login, `Desktop.onLogin` doesn't fire for the first login, and the launch bar is reused across logins in the same tab. The button has no feature id in the DOM, so it is found with `LaunchBarContainer.getButtonByID`.
- `dynamicQueriesDojo/` — registered by ICN as the `dynamicQueriesDojo` module path; each widget has an HTML template in `templates/` loaded via `dojo/text!`.
  - `DQ.js` — the feature pane, extends `ecm/widget/layout/_LaunchBarPane` (implement `loadContent`/`reset`; `isLoaded`/`needReset` control lifecycle). Leading pane: the repository configured for the plug-in (`repositoryId`, read-only; fetched with `SettingsClient.getSettings`, "Nueva consulta" and "Proyectos" stay disabled until it resolves in the desktop), "Nueva consulta" and a `dijit/Tree` whose "Consultas guardadas" folder holds one subfolder per project with its queries, from `DqApiClient.listProjectQueryCompose` (`refreshTree`; projects and queries sorted by name, inactive ones marked; query items are keyed by `projectQueryId` because a query can belong to several projects; queries without a project don't appear). The tree is refreshed after saving a query and after closing "Proyectos". Clicking a query opens it; the context menu offers Abrir / Ejecutar / Eliminar (Eliminar first deletes the query's project associations: the service refuses with 409 to delete an associated query). `openSavedQuery` parses the query's `config` (the stored definition) and rebuilds the ICN `SearchTemplate` (`QuerySerializer.toSearchTemplate`); queries whose `config` isn't a definition (created outside the plug-in) can't be opened and reuses the tab if the query is already open. Center: a `StackContainer` switching between an empty state and a `TabContainer` of `QueryTab`s. Access: if `canDesign` is false the pane shows only a no-access notice (`dqAccessDenied` class) — this only hides the UI; the microservice is called from the browser and doesn't know the ICN user. ICN reuses the pane across logout/login in the same tab, so `onLogout` clears it (tabs, tree, permission) and `onLogin` reloads it if selected.
  - `DQResults.js` — "Resultados de consultas": runs the queries of a project. Top bar: a select of the active projects with at least one active query (query and association; from `DqApiClient.listProjectQueryCompose`, `baseUrl` from `SettingsClient.getSettings`; on failure `isLoaded` goes back to false so reopening retries; like `DynamicQueries.js` it polls `Desktop.connected`/`userId` every 500 ms, because opened from the URL (`&feature=DQResults`) ICN selects the pane before login and never calls `loadContent`, and it clears the pane when the user changes), the wildcard fields of the project's queries (`QuerySerializer.getQueryParameters`, merged by name: the same `#Name` in several queries is one field; sorted by the designer's `parameterOrder`, the lowest across queries, unordered ones last in order of appearance; widget by data type, all required; Enter searches; if the wildcard's property has a P8 choice list in its query's class — `getQueryParameters` returns `className`/`property`; looked up with `repository.getContentClass(cls).retrieveAttributeDefinitions(cb, true, onError)`, once per class, `choiceList.choices` `{ displayName, value }`, nested groups flattened — the field is a required `Select`; for a class that doesn't exist ICN 3.0.10 calls neither callback, so it gives up after 10 s and uses a text field) and Buscar, which fills each query's CE SQL (`QuerySerializer.fillParameters`) and sends them to `ExecuteQueriesService` with the association `config` as grouping path. `buildTreeData` turns the response (shape of the consulta general's `queryContent`) into the `dijit/Tree` items, splitting comma-separated folder names and recursing into nested virtual folders. Failed or truncated queries are listed under the form. Whenever the fields or the message change, `_layoutSearchPane` re-lays out the `BorderContainer`: its top region keeps the height it was drawn with, and the center region would cover the fields. The tree items and viewer still come from `GQViewFeature` of the PortalUpICN plug-in. Clicking a document calls `DocumentPropertiesClient.getProperties` (`DocumentPropertiesService`; no longer `/portalUpApp`): the properties go to the grid (display names) and the document is shown with ICN's `bookmark.jsp` on the `LPADocViewer` desktop or, when `s3` and `file` (base64 content), rendered in the browser; an S3 document without `file` shows `fileError` in the viewer (only the last clicked document's response is applied) (TIFF via `UTIF.js`, a non-AMD script that sets `window.UTIF`; PDF and images as `blob:` URLs because ICN's CSP doesn't allow `data:`). Those constants are at the top of the module. Unlike the original, ids are per instance (attach points / `${id}_…`) and all CSS is under `.dqResultsPane`, since `GQViewFeature` may be installed on the same ICN.
  - `DocumentPropertiesClient.js` — promise wrapper over `Request.postPluginService` for `DocumentPropertiesService` (`getProperties(documentId)`); rejects with `{ code, message }`.
  - `ExecuteQueriesClient.js` — promise wrapper over `Request.postPluginService` for `ExecuteQueriesService` (`execute(queries)`); rejects with `{ code, message }`.
  - `QueryTab.js` — one tab per query: a subclass of ICN's `ecm/widget/search/SearchBuilder` (criteria, Buscar, results) with the parts DQ doesn't use hidden via the `dqHiddenAction` class: P8 save buttons, "Buscar en"/"Opciones de búsqueda" (always root folder, documents, released version), "Visualización de resultados", "Mostrar todas las propiedades", "Buscar en varias clases" and "Incluir todas las propiedades" in the class dropdown (hidden, unchecked and disabled, so multi-class mode can't be triggered), the "Valores avanzados" gear of each criteria row (CSS on `.attributeDefintionWidget .optionIcon`, since ICN creates rows dynamically), and in the results toolbar "Añadir documento", "Exportar todo" and "Acciones" (`getContentListModules` configures the `Toolbar2` module). `DQ` acts as its `tabContainer`/`parentPane` (`closeTab`, `openTab`, `openSearch`). ICN ignores the class of a new search (`isNew()`), so the module patches `BasicSearchDefinition._initContentClassSelector` to make templates from `QuerySerializer.toSearchTemplate` (`dqRestoreClass`) look not-new only while the class selector initializes; when the form is ready the tab applies "Incluir subclases" from the definition (`dqIncludeSubclasses`). The ICN search API as verified on 3.0.10 is documented in `docs/icn-search-api.md`. "Ver JSON" shows the query definition. "Comodines" (count in the label) opens `ParametersDialog` (with `serialize(…, keepLabels)` so it shows the conditions' display names); the tab keeps the choice in `parameters` (`{ key: { name, order } }`), passed to `serialize`, and `DQ.openSavedQuery` rebuilds it from the saved definition (`QuerySerializer.getWildcards`).
  - `ParametersDialog.js` — "Comodines" (ICN `BaseDialog`): lists the conditions that have a value (`QuerySerializer.getConditions`) and lets the user mark which ones are wildcards — asked for when the saved query is executed — their names (letters/digits/_, unique) and "Orden", the position of their field in "Resultados de consultas" (integer 1–999, unique; preset to the next free one; saved on the condition as `parameterOrder`). Conditions whose operator takes several values (IN, BETWEEN) or none (IS_NULL) can't be wildcards. The condition keeps its value as the sample used by Buscar in the designer.
  - `QuerySerializer.js` — both directions between the ICN builder and the API contract's `QueryDefinition`. `serialize(searchDefinition, repository, parameters, keepLabels)` reads the form without running the search; `build(state)` (pure) converts it and validates. `toIcnSearch` (pure) / `toSearchTemplate` go back: contract → the JSON ICN uses for saved searches → `SearchTemplate` the builder can open. The saved definition is kept compact (it used to be limited to 1024 chars): no condition `label` (except wildcards), no `documentClass.displayName`, no `scope` for the root with subfolders, and `serialize` doesn't include `resultsDisplay` (hidden in DQ, always the class default). `toCeSql(definition)` (pure) produces the P8 CE SQL: `Id` + result columns (`{NAME}` → `DocumentTitle`), class `WITH INCLUDESUBCLASSES|EXCLUDESUBCLASSES`, conditions/groups, `INFOLDER`/`INSUBFOLDER`, version (`VersionStatus = 1` / `IsCurrentVersion = TRUE`), `ORDER BY`; datetimes as UTC literals (`20260101T050000Z`); `IN` is expanded to `=` … `OR` (single-valued properties). Wildcards: a condition marked as a wildcard keeps its sample `values` and gets `parameter: "Name"`; `toCeSql` writes `#Name` instead of the value, the `CG_CFG_QUERY` convention of the consulta general backend (`'#Name'` quoted for STRING and inside LIKE patterns, unquoted for numbers/dates/booleans/GUIDs; contract details in the `Condition.parameter` schema). Wildcards are keyed by property + occurrence among conditions with a value (`"NroIdentificacion#1"`, `getConditions`); `getParameters(definition)` lists them for whoever executes the query, sorted by `parameterOrder` (`sortParameters`: unordered ones last, stable); `getQueryParameters(query)` does it for a saved query (from its definition, or the `#Name` tokens of its CE SQL if `config` isn't one: quoted → STRING, unquoted → number) and `fillParameters(cesql, parameters, values)` replaces them like the consulta general but escaped (`''` inside quotes, typed CE SQL literals outside; a name that is a prefix of another doesn't clobber it). `toGroupingConfig`/`fromGroupingConfig` convert the results grouping path ("A,B,C") to/from `{ vnRoot: "A,B,C" }`, the `DSCONFIG` format of `CG_CFG_QUERY` (not JSON). Pure parts are unit-tested.
  - `SaveQueryDialog.js` — "Guardar consulta" (ICN `BaseDialog`): saves `{ name, cesql, config, status }` with `DqApiClient.createQuery`/`updateQuery` (update when the query has an `id`) and then, with the query id, its project association (`/project-query`, `{ projectId, queryId, config }` where `config` is the "Ruta de agrupación" field as `{ vnRoot: "…" }`, i.e. the folders the results are grouped in). The user enters name (max 100), project (required select of active projects), grouping path (required, comma-separated folders, no quotes) and status; when editing, the current association preselects project and path (older free-text configs are shown as they are) and is updated only if they changed. Wildcards are listed read-only. If the association fails for a new query, the query is deleted again (if that also fails, the dialog keeps its id so a retry updates it). `cesql` (max 4000) comes from `QuerySerializer.toCeSql` and is shown read-only; `config` is the definition as JSON (a CLOB in the service, no limit; the association `config` is still max 1024). Over a limit, or with definition errors, Guardar stays disabled with the reason. `QueryTab` keeps the saved query in `savedQuery` and fires `onQuerySaved`.
  - `ProjectsDialog.js` — "Proyectos" (ICN `BaseDialog`, button in the leading pane below "Nueva consulta"): full CRUD of projects. A toolbar (Nuevo / Editar / Eliminar / Actualizar + status filter), a plain HTML table as the grid (click selects, double-click edits) and an inline fieldset form between the toolbar and the table (name and description required, max 100 each; status ACTIVE/INACTIVE). Errors and confirmations go to the dialog's `setMessage`; delete asks with `ConfirmationDialog`.
  - `DqApiClient.js` — `dojo/request/xhr` client for the DQ microservice, called from the browser (not through ICN); `baseUrl` (`projectsApiUrl`) is set by `DQ` from `SettingsClient.getSettings`. Projects: `listProjects(status?)`, `getProject`, `createProject`, `updateProject`, `deleteProject` over `{baseUrl}/project[/{id}]` (`{ id, name, description, status, createdAt }`). Queries: `listQueries(status?)`, `getQuery`, `createQuery`, `updateQuery`, `deleteQuery` over `{baseUrl}/query[/{id}]` (`{ id, name, cesql, config, status }`). `listProjectQueryCompose()` → `GET {baseUrl}/project-query-compose` (projects with their `queries`, each with `projectQueryId`/`projectQueryConfig`/`projectQueryStatus`). Project–query associations: `listProjectQueries({ projectId, queryId, status })`, `createProjectQuery`, `updateProjectQuery`, `deleteProjectQuery` over `{baseUrl}/project-query[/{id}]` (`{ id, projectId, queryId, config, status, createdAt }`; 409 if the pair exists); treats HTTP status 0 as a failure (dojo/request counts it as success); rejects with `{ status, code, message }` (maps the service's `ErrorResponse`, including `details`).
  - `SettingsClient.js` — promise wrapper over `ecm/model/Request` for `SettingsService` (`getSettings`); rejects with `{ code, message }`.
  - `ConfigurationPane.js` — plug-in–level admin config (extends `ecm/widget/admin/PluginConfigurationPane`): repository of the queries (required; a select filled with ICN's P8 repositories via `ecm.model.admin.appCfg.getRepositoryObjects`), the DQ microservice base URL, the groups allowed to use the designer (`designerGroups`, empty = everyone) and the S3 download service (`s3DownloadUrl`, e.g. `https://apiprivada-qa.proteccion.com.co/gce-alm/documentos/s3descarga`, and `s3ApiKey`, a password field; never commit the key: this repo is public).
  - `FeatureConfigurationPane.js` — per-desktop feature config; `load()` reads `this.configurationString`, `save()` must serialize values back into it.

String identifiers are the glue between the Java and JS halves: the Dojo module name, widget class names, file names and the plugin/feature ids returned in Java must match the JS `define`/`declare` names and file paths exactly. Plug-in and feature ids must be alphanumeric (used in URLs). Keep `declare` names in the lowercase `dynamicQueriesDojo.*` namespace.

CSS in `DynamicQueries.css` is loaded globally into ICN, so scope every feature rule under `.dqPane`; dialogs are attached to `<body>`, so scope theirs under their own `dq*Dialog` class.

## graphify

- For codebase questions, first run `graphify query "<question>"` when graphify-out/graph.json exists.
